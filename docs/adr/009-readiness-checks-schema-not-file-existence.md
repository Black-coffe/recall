# ADR-009: Робота ніколи не плутає порожній файл БД зі схемою, що готова

- Status: proposed
- Date: 2026-09-06
- Spec: docs/specs/config-registry-profiles

## Context

Із `## Plan deltas` спека `config-registry-profiles` (2026-09-06, «`/api/health` перейшов на
спільну з `/api/ready` перевірку БД, хоча Non-goal `config-registry-fix-03-робота-contract`
(раунд 1) забороняв чіпати `/api/health`»):

> Тригер: `lead-review` раунд 2 — знахідка N3 ...: БД-файл, створений порожнім, давав
> `/api/health` `database:"ok"`/`/api/ready` `ready:true` без жодної схеми (обидва ендпоінти лише
> пробували відкрити з'єднання, яке саме створює файл).
>
> Рішення: `app/blueprints/system.py::_check_database_ready(db_path) -> bool` — єдина перевірка для
> обох ендпоінтів: `''`/`None`/`':memory:'` → `False` без винятку; інакше URI `mode=rw` (без `c`,
> файл не створюється) + `SELECT MAX(version) FROM schema_versions`; `True` лише якщо є рядок і
> `>= 1`. Тіло і коди відповіді `/api/health` не змінені (тільки джерело статусу `database`),
> `app/db/connection.py` (гарячий шлях) свідомо не чіпали — окремий хелпер у `system.py`.

## Options

1. `mode=rw` прямо в `get_db_connection()` (гарячий шлях застосунку) — відкинуто: означало б
   прапорець «створювати/не створювати БД» у кожному виклику гарячого шляху заради одного вузького
   споживача (робота).
2. Лишити `/api/health` як був, із записом сценарію в `## Descoped` — відкинуто: сценарій
   «монітор створює порожню БД, обидва ендпоінти зеленіють» дешево закривається окремим хелпером,
   тож лише документувати його замість виправлення не варте.

## Decision

Перевірка готовності БД — і для `/api/ready`, і для `/api/health` — відкриває файл через URI
`mode=rw` (без `c`, без автостворення) і читає `SELECT MAX(version) FROM schema_versions`;
готовність визнається лише коли повернувся рядок з версією `>= 1`. Обидва ендпоінти йдуть через
один і той самий хелпер (`_check_database_ready`), а не через відкриття зʼєднання гарячого шляху
(`get_db_connection`), яке саме створює файл при відкритті.

## Consequences

Легше: жоден незахищений ендпоінт (моніторинг, health/ready-перевірки) більше не може випадково
створити порожню бойову БД самим фактом звернення, і жоден з них не звітує «готово», доки міграції
справді не пройшли. Важче: робота-шлях тримає власний хелпер відкриття БД окремо від гарячого
шляху застосунку — два способи відкрити той самий файл, синхронізовані лише спільною назвою функції,
не спільним кодом з `app/db/connection.py`.

## Invariants created

Жоден HTTP-ендпоінт, доступний без авторизації (health/ready-перевірки і подібні), не відкриває БД
у режимі, що створює файл за його відсутності. Готовність БД визначається наявністю пройдених
міграцій (`schema_versions`), а не самим фактом, що з'єднання відкрилось.

## Revisit when

Гарячий шлях (`app/db/connection.py`) отримає власний read-only режим (`mode=ro`/`mode=rw` без `c`
як стандартна опція виклику) — тоді робота зможе піти через нього напряму, і окремий хелпер у
`system.py` стане дублюванням, яке варто прибрати.

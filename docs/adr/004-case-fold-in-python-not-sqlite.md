# ADR-004: Згортання регістру для порівняння тексту — лише в Python, ніколи в SQLite `lower()`

- Status: proposed
- Date: 2026-09-04
- Spec: docs/specs/grep-explainability

## Context

Із `## Plan deltas` (D1) спека `grep-explainability`:

> **Кирилиця в `ignore_case` (знахідка 1, критична).** Історія 01 диктувала SQL
> `instr(lower(text), lower(?))` під заголовком «це не вільний вибір» — і саме цей рядок і є дефект:
> SQLite `lower()` згортає лише ASCII, тож `grep('андрій')` дає 0 на чанку зі словом `Андрій`, тоді
> як regex-режим той самий запит знаходить. Памʼятка проєкту про це існувала до планування
> (`SQLite LOWER не сворачивает кириллицу`) і була проігнорована планом.
> **Рішення:** обидва режими згортають регістр у Python (`str.casefold`), а не в SQL. Буквальний і
> regex-шлях зобовʼязані означати одне й те саме під одним прапорцем.
> Відкинуто: `lower(x) COLLATE NOCASE` (та сама ASCII-межа) і ICU-розширення (нема в збірці).

Це не перший раз, коли цей самий дефект стається: та сама пастка (`SQLite LOWER не сворачивает
кириллицу`) уже була знайдена й зафіксована в памʼяті проєкту під час роботи над злиттям сутностей
(`memory/entity-merge-moves-names-to-aliases.md`) і все одно повторно потрапила в план цієї спеки.
Архів переважно кириличний (дзвінки, Telegram українською/російською) — будь-яке майбутнє порівняння
тексту без урахування регістру наступить на ту саму межу, якщо рішення не зафіксоване як інваріант,
а не як пам'ять, яку треба щоразу пригадувати заново.

## Options

1. `SQL lower()` / `LOWER(x) COLLATE NOCASE` — найпростіше в SQL, але згортає лише ASCII;
   мовчки трактує кирилицю як чутливу до регістру. Відкинуто планом.
2. ICU-розширення SQLite для регістронезалежного `lower()` з підтримкою Юнікоду — коректне рішення,
   але розширення відсутнє в поточній збірці SQLite проєкту. Відкинуто планом.
3. Згортання регістру в Python (`str.casefold()`) до або під час порівняння, ніколи в SQL-виразі —
   коштує зчитування ширшого набору рядків у Python-код, зате коректне для кирилиці й латиниці
   однаково і не залежить від збірки SQLite. Обрано.

## Decision

Будь-яке порівняння тексту без урахування регістру над цим архівом (пошук, дедуплікація сутностей,
майбутні тулзи) згортає регістр у Python (`str.casefold`), а не покладається на SQL `lower()`/
`LOWER(...) COLLATE NOCASE`. Буквальний і regex-режим одного інструменту зобовʼязані давати
однаковий результат під одним прапорцем регістронезалежності.

## Consequences

Легше: код, що порівнює текст незалежно від регістру, коректний одразу на кириличному й латинському
корпусі без додаткових залежностей (ICU) у збірці. Важче: порівняння, які раніше виконувались
цілком у SQL (і потенційно використовували індекс/сортування на боці двигуна), тепер вимагають
зчитування ширшого набору рядків у Python перед фільтрацією за регістром — ціна, яку ADR-005 прямо
адресує для сканувальних тулз (робота обмежується кількістю переглянутих рядків і дедлайном, а не
покладається на SQL `LIMIT`).

## Invariants created

Жоден новий код, що порівнює текст без урахування регістру над цим архівом, не викликає SQL
`lower()`/`LOWER(...) COLLATE NOCASE` як механізм згортання регістру. Згортання — виключно
`str.casefold()` у Python-коді, застосоване однаково до всіх режимів одного інструмента.

## Revisit when

Проєкт переходить на СУБД чи розширення SQLite з коректним Юнікод-згортанням регістру «з коробки»
(напр. увімкнене ICU-розширення в збірці) — тоді вибір можна переглянути з урахуванням реальної
вартості на гарячому шляху.

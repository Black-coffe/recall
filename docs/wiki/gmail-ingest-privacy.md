# Gmail ingest: read-only channel, password and masking invariants

Mail is the third live ingest channel (next to recordings and Telegram). Code map: `memory/map/services-mail.md` (connect links: § Connect links; HTTP: `memory/map/blueprints.md` § connect.py). One record per email (`transcriptions.source_type='email'`, `mail_*` columns, schema v52); attachments are ordinary `document` records linked through `mail_attachments`.

Invariants:
- The channel is read-only toward Gmail: `ReadOnlyImap` exposes a fixed set of methods, mailboxes are opened with EXAMINE (`select(readonly=True)`), messages fetched with `BODY.PEEK[]` (`\Seen` untouched). There is no passthrough to the connection and no `smtplib`.
- The app password exists only in the OS credential store (`keyring`, service `Recall Gmail`, username = normalised address). It is never in the DB, `.env`, settings registry, logs, git, the mirror, backups or any dict `mail_accounts` returns; `mail_accounts.get_password` is its only reader. `POST /api/mail/accounts` never echoes or logs it; `MailError` text is scrubbed, and a failed login drops the server text entirely.
- Residual risk, accepted: Windows Credential Manager does not protect the password from other processes under the same Windows account. Mitigation is user-side (one app password per mailbox, revoke on suspicion); the Mail screen says so.
- Nothing is ingested until the owner enables a label (`mail_labels.enabled`, new rows default 0). Disabling a label stops future sync only; deleting an account removes account, label rows and keyring entry, while ingested emails and attachments stay. Soft disconnect (4.24.0, `mail_accounts.disconnect_account`) drops only the keyring entry and disables all labels; cursors and records stay, and a reconnect does not re-enable labels.
- Masking before any write: body, subject (and so title/`source_name`) and attachment text go through `mail_parse.mask` (`screen_secrets` + mail phrasings: labelled passwords/PINs/tokens, one-time codes, Bearer/Basic). Text attachments are masked before the file hits disk; binary attachment files are kept as received and only their parsed text is masked. The pipes mask (IBAN/phones/amounts) is NOT applied to mail.
- Claude is off by default: `mail_enrich` (set from the label's `enrich` toggle, also on attachment documents) is honoured by `enrichment.py` (`mail_enrich == 0` -> skipped `mail_enrich_off`; backfill and list queries use `mail_enrich IS NOT 0`). Emails embed only (job `mail_embed`).
- A failed message never advances the label watermark past itself: `last_uid` stays below the smallest failed UID so it is refetched.
- Dedup is `(mail_account_id, mail_message_id)` (unique partial index); one email under two enabled labels is one record owned by the label that saw it first. Attachments dedup globally by text hash; the same file in two emails is one document with two links.
- MCP reads mail through `email_status` (a proxy of `GET /api/mail/status`, whitelisted keys only); email records carry an `email` block in `get_transcript`/`list_recent`/`search_history`. Since 4.19.0 MCP has two narrow mail/settings write tools, `mailbox` and `settings` (a third write, `video_analyze`, arrived in 4.20.0 and is unrelated to mail), plus four gated D tools since 4.24.0 (`mailbox_backfill`, `mailbox_label_enrich`, `mailbox_disconnect`, `settings_remove_anthropic_key`); none can carry a secret (next invariant).
- Connect link path (4.19.0): the app password (and the Anthropic key) is typed only on a one-time local page, `http://127.0.0.1:<port>/connect/<kind>/<token>`; the MCP and the chat never see it. `mailbox(connect, address)` / `settings(connect_anthropic_key)` only return the link. Links live in memory (`connect_links`), 600 s, die on success, on the 3rd failed attempt or at expiry, and one new link per kind+address replaces the older. The page answers only direct loopback requests (no proxy headers, loopback `Host`, same-origin `Origin` on POST), sends `no-store`/`same-origin` referrer/`DENY` framing, and never logs or renders the secret back (only `MailError.code`). It reuses the same code as the Settings screen (`mail_accounts.connect_account`, `settings_secrets.save_anthropic_key`), so the "login first, store second" and keyring-only rules above hold unchanged.
- Secret-shaped MCP arguments are refused: `_SecretGuardMiddleware` runs `secret_shape.find_secret_args` over every tool call before the call log can see it (`SECRET_IN_ARGUMENT`, names only); `POST /api/mail/connect-link` re-checks the address. The check is a heuristic. Grouped 4x4 letters and `sk-ant-` are refused on every tool; the bare 16-letter token not followed by `@` is refused only on write (W/D) or unregistered tools (`strict=False` for read tools, 4.20.0), so a write argument can still be refused for a harmless 16-letter word.
- Costly or destructive mail actions are gated routes for EVERY caller (4.24.0): turning a label's `enrich` on is `POST /api/mail/labels/<id>/enrich`, a sync deeper than 12 months is `POST /api/mail/backfill` (13..120), soft disconnect is `DELETE /api/mail/accounts/<id>/credentials`, hard delete stays `DELETE /api/mail/accounts/<id>` (UI only, no MCP tool); each waits for the approval dialog (`approval-gate.md`). Plain `PATCH enrich:true` and `/sync` months>12 answer 400 `USE_GATED_ROUTE` whoever asks; `enrich:false` stays ungated.
- MCP callers (`X-Recall-Actor: mcp`) additionally cannot move a label out of a private direction into an open one (`privacy.category_change_exposes`, fail closed), and the first load of a label they enable is capped at 12 months (`first_months_cap`).
